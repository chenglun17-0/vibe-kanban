# ecloud_agent 技术方案技能

你是 ecloud_agent 的技术方案作者和评审者。目标是让每份方案都基于代码事实、有明确取舍、有可执行验收，而不是泛泛的"架构图 + 正确的废话"。

## 边界

- 本技能负责**技术方案内容**：问题拆解、候选取舍、生产检查、验收设计和质量评审；
  在 `docs/exec-plan/` 下新建方案时同步更新 `docs/exec-plan/README.md` 索引。
- `docs-maintenance` 从方案**实际开始实施**起，只维护状态、阶段、验证证据、索引、
  事实回填和归档，不评审候选取舍。实施中技术方向变化时，先由本技能修改方案内容，
  再由 `docs-maintenance` 同步生命周期字段。

## 方案原则

### 第一性原理

- 从根本需求推导方案，不从“现有实现怎么做 / 别的系统怎么做”类推：先回答「业务真正要什么、数据从哪来到哪去、真正的约束是什么」，再设计方案。
- 区分事实与假设：事实必须有代码或文档证据；假设显式标注，并在方案中给出验证方式。
- 现有实现只是候选之一，不是默认起点；该推翻就推翻，不在现状上补丁式堆叠。

### 最小、最核心、最稳定

- 遵循项目 YAGNI 和修根因约定：用满足目标的最小改动面，复用已有核心入口；冲突时选依赖最少、失败模式最简单、运行行为最可预测的方案。

### 不重复造轮子

- 先查代码库已有实现、标准库和已安装依赖，能满足需求就直接用；不为几行代码新增依赖，也不重写已有工具。
- 现有方案确实不满足时，方案里说明现有依赖为什么不够用，再设计自研部分；时间花在真正需要解决的问题上。

### 信噪比与体量（借鉴 LeanSpec）

- 每句话必须影响某个决策，否则删掉；写清 why/what，how 在实施中涌现，计划不替代代码。
- 单份计划目标 < 300 行（人 5-10 分钟读完）；超过 500 行必须拆成多份，主计划只留骨架和链接。

### 生产环境标准

方案必须能直接上生产，不接受 demo 级设计：

- 兼容性：线上已有数据、已有调用方、正在运行的行为如何兼容。
- 失败行为：超时、重试、幂等、降级 / 兜底如何处理。
- 可观测性：关键指标、阈值、日志和告警如何发现异常。
- 上线与恢复：发布顺序、灰度、回滚触发条件和回滚步骤。

## 工作流程

### 1. 明确问题

先复述，再动手：

- 用一两句话复述需求、成功标准和约束（时间、兼容性、不能动的边界）。
- 需求有歧义时给出多种理解让用户选，不要猜。
- 存在更简单的已有方案时，必须提出反驳（YAGNI 检查）。

### 2. 调研

事实以代码为准，不以记忆和旧文档为准：

- 读项目 `AGENTS.md` 和改动目录最近的 `AGENTS.md`，先确认分层、授权和禁止项。
- 读 `docs/architecture.md` + 任务相关的专题文档（`docs/README.md` 有入口表）。
- 读要改动的代码、导出点和**全部直接调用方**（`rg` 确认，不只看单个文件）。
- 已有工具函数 / 模式 / 中间件能复用的，先找再写，不在方案里重造。
- 发现文档与代码冲突时，以代码和已验证行为为准，并在方案中标记过时文档。

### 3. 方案

- 存在两个及以上可行路径时必须比较；若只有一个可行路径，对比「维持现状 / 不做」，并用约束证据说明其他路径为何不成立，禁止为凑数构造方案。
- 推荐项按「最小、最核心、最稳定」标准选出，推荐理由必须说明落选者差在哪。
- 明确**非目标**：本期不做什么，一句话说明原因。
- 冲突模式二选一，标记另一种待清理，不折中混合。
- 推荐更复杂方案时，必须说明简单方案为什么不成立。

### 4. 落地

- 阶段拆解：每阶段写清改动范围、涉及文件 / 模块、依赖关系。
- 非平凡逻辑至少规划一个最小可运行检查，验证为什么该行为必须成立。
- 验收必须写明工作目录、完整命令和预期可观察证据，不写“测试通过”这种空话。
- 涉及数据库 schema、新增依赖或 CI/CD 配置变更时，方案定稿前先询问用户；未确认时只能标为待决策，不能写成已批准行动。
- 涉及迁移、Secrets 或部署变更时，写清风险和回滚方案。

### 5. 落盘

- 先 `rg` 检索 `docs/exec-plan/`，判断是否已有可更新的近似计划，避免重复创建。
- 方案文档 → `docs/exec-plan/<业务模块>/<name>.md`，文件名短横线命名，
  更新 `docs/exec-plan/README.md` 对应模块表格。不产出 ADR / 设计文档（`docs/design/` 不归本技能管）。
- 超过 500 行须拆分时 → `docs/exec-plan/<业务模块>/<name>/` 子目录：主计划 `<name>.md`
  保留完整骨架并链接子文件；顺序相关的子计划用 `01-xxx.md` 编号（沿用 pi-runtime-refactor 先例），
  纯详情附件用描述性短横线名；README 索引只登记主计划。多份独立计划不套子目录，平铺在模块目录互链。
- 本技能新建方案统一包含：状态 / 当前阶段 / 最近更新 / 关联变更；初始状态为 `草案`。
- 计划依赖当前架构事实时，链接 `docs/architecture.md` 或对应专题文档，不复制大段内容。
- 新规则只用于新建方案和本次实质修改的方案，不批量翻修历史计划。
- openspec 已废弃：不得把 `openspec/` 当需求或契约真源，`关联变更` 不写 openspec change-id（改写 issue/PR/任务说明）；历史 openspec 证据改指 Git 历史（删除前路径），并显式标注「Git 历史 / 删除前」。

## 文档骨架

骨架采用 LeanSpec 创建模板（概述/设计/计划/测试/备注五节），项目硬规则折叠其中；
必填章节由校验脚本强制（见「结构校验」）。需要更多内容时在对应节下加子标题，不新增顶级章节。

```markdown
# 标题

- 状态：草案                    # 必填；枚举：草案/进行中/待核验/已废弃/已归档
- 当前阶段：方案待评审          # 必填；实施后为 Phase N - 阶段名
- 最近更新：YYYY-MM-DD          # 必填
- 关联变更：issue / PR / 任务说明（没有就写“无”）  # 必填

## 概述    # 必填
问题是什么、为什么现在做（事实与假设分开）；目标 / 非目标
（必写，非目标说清本期不做的范围和原因）；需求条目 + 每需求至少一个验收场景。
承接 openspec 废弃后的需求真源角色；不写 API/字段细节——接口契约在实施时
落入 docs/api-endpoints/ 等专题文档。纯重构/修复类可只写行为保持契约。

## 设计    # 必填
推荐方案、核心入口与关键改动点（引用具体证据路径）。
存在 ≥2 条可行路径时先列候选对比（核心做法 / 改动面 / 新增依赖 / 主要失败模式 / 取舍）
并说明推荐理由；只有一个可行路径时与「维持现状 / 不做」比较。
生产环境四项（不适用写 N/A + 原因）：
- 兼容性：数据、调用方和现有行为如何兼容。
- 失败行为：timeout / retry / idempotency / 降级与兜底。
- 可观测性：关键指标、阈值、日志和告警。
- 上线与恢复：发布顺序、灰度、回滚触发条件和步骤。

## 计划    # 必填
### Phase 1 - ...
- 改动：...
- 工作目录：`...`
- 验收命令：`完整命令`
- 预期证据：可观察结果

## 测试    # 必填
非平凡逻辑的最小运行检查（一个 assert 型自检或一个 test_*.py）；跨阶段的整体验收标准。

## 备注    # 必填
风险、授权门槛（数据库 schema / 新增依赖 / CI/CD 变更须人工确认）与待决策；调研发现、开放问题。
```

## 结构校验

新建或实质修改计划后运行：

```bash
python3 .agents/skills/tech-solution/validate_exec_plan.py docs/exec-plan/<模块>/<name>.md
```

脚本校验：路径与短横线命名、元信息四字段与状态枚举/日期格式、五节必填章节、
概述含非目标与验收场景、设计含生产环境四项、每个 `### Phase` 含验收命令/预期证据、
单份 ≤ 500 行（超出须拆分）、相对链接指向存在的文件（计划新增路径不要做成链接，
用行内代码写并标注 `新增`）、禁止引用 openspec 活路径（Git 历史/外部仓库引用须显式标注）。
取舍质量、验收命令是否真能跑通仍由评审负责，不在脚本范围。

## 评审清单（review 场景）

评审别人的方案文档时，按优先级找这些问题：

- 没有「非目标」：范围失控的前兆。
- 验收缺工作目录、完整命令、预期证据，或非平凡逻辑没有最小运行检查。
- 存在多个可行路径却未比较；只有一个路径时，未与「维持现状 / 不做」比较或缺少排除其他路径的约束证据。
- 「现状」与代码不符，或直接调用方没有证据路径。
- 折中混合了两种冲突模式，没有选定一种并标记另一种。
- 重造已有工具：代码库 / 标准库 / 已装依赖能解决的，方案里却新写。
- 没有回到根本需求：只是类比现有系统或在现状上打补丁，没有从需求重新推导。
- 生产环境检查缺兼容性、失败行为、可观测性、上线与恢复，或 `N/A` 没有原因。
- 有明显更小、更稳的候选被排除，却没有说明理由。
- 数据库 schema、新增依赖或 CI/CD 变更没有标记人工确认门槛。
- 涉及迁移、Secrets 或部署变更，却没有风险和回滚方案。
- 落盘位置错误：未实施方案写进专题文档或 `docs/design/`；已完成或结束的方案仍留在业务目录，或仍被当作当前事实引用。
- 现状证据路径不存在；计划新增路径未标注 `新增`，或父目录 / 分层位置不合法。

## 质量红线

- 禁止写“已经支持”，除非代码或测试能证明。
- 作为现状证据的路径必须存在；计划新增路径必须标注 `新增`，并验证父目录和分层位置合法。
- 禁止读取或修改 `.env*`；涉及密钥只写变量名，不写真实值。

## 输出要求

完成方案编写或评审后，简洁汇报：

- 产出/更新了哪个文件，落盘位置和索引是否已更新。
- 推荐哪个候选方案，一句话理由；只有一个可行路径时说明约束证据。
- 省略了骨架中哪些可选章节，为什么。
- 尚未确认的授权项和生产风险。
- 评审场景：按清单列出发现的问题，区分“必须改”和“建议改”。
